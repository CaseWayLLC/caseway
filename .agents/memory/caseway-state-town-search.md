# Caseway landing location search: State then Town

The landing discovery search is two searchable comboboxes: pick a US **state** first (`StateCombobox`, options from `US_STATES` in `constants.ts`), then a **town** scoped to that state (`TownCombobox`). The town field is disabled until a state is chosen; "Find lawyers" is disabled until both a state and resolved coords are set; changing the state clears the town + coords.

**Town picker is dataset-backed, not geocoded (the key decision):** the town list is a static per-state dataset shipped in `artifacts/solomatch/public/towns/<ABBR>.json` (`[{name,lat,lng}]`, coords 4-dp), generated by `pnpm --filter @workspace/scripts run gen:towns` (`scripts/src/gen-towns.ts`) from the `country-state-city` package. Coordinates are baked in, so **picking a town sets `searchCoords` directly with zero geocoding round-trip**. `TownCombobox` lazy-fetches the per-state file via `import.meta.env.BASE_URL` and caches it per state.
**Why:** the user explicitly wanted to pick a state and then **browse EVERY town** in a dropdown (not type-only). Geocoders (Photon/Nominatim/Google) cannot enumerate a state's towns, so a bundled dataset is the only way to show the full browsable list. This replaced the earlier keyless type-to-search-via-Photon landing approach.

**Generator filter — drop county-equivalents:** `gen-towns.ts` filters names matching `/\b(county|parish|borough|census area|municipality)\b/i`. This removes county rows, Louisiana **parishes**, and Alaska **boroughs / census areas / municipalities** — which `country-state-city` mixes in as "cities". Real cities still survive because they ALSO appear under their plain name (verified: "Anchorage", "Juneau", "New Orleans", "Baton Rouge" all remain). ~16.5k towns across 51 files; biggest states TX ~1023, CA ~1065, NY ~992.

**Rendering the full list — virtualize, don't use cmdk:** several states have ~1000+ towns; cmdk (used by `StateCombobox`) registers an effect per item and degrades badly at that size. `TownCombobox` therefore **drops cmdk** and renders the FULL filtered list with `@tanstack/react-virtual` (`useVirtualizer`, `ROW_HEIGHT` 36, fixed-height absolutely-positioned rows) inside a Popover, with its own search `<input>` and manual ArrowUp/ArrowDown/Enter/Escape keyboard nav (`scrollToIndex` on move). No render cap — a footer shows the total town count when not searching. `state-combobox.tsx` / `command.tsx` still use cmdk.

**Stale-fetch guard:** `reqRef` (a monotonic token) is bumped at the **top of the state-change effect on every change**, and each fetch's `.then/.catch/.finally` only commits state if `reqRef.current === id`. So a slow fetch for a previously-selected state can never overwrite the current list after a fast state switch. (Bumping only on uncached fetch was the earlier bug.)

**Gotcha — transient invalid-hook on first add:** the first time `@tanstack/react-virtual` was added, the Vite HMR browser console threw a one-time `Invalid hook call` / `Cannot read properties of null (reading 'useReducer')` at `useVirtualizerBase` during on-the-fly dep re-optimization. It is **benign** and clears after a workflow restart / full page reload — NOT a duplicate-React problem (single `react@19.1.0`; react-virtual consumes it as a peer dep).

**Scope:** landing search only. The attorney **signup** form still uses `AddressAutocomplete` + `geocode.ts` state-verification (it needs a full street address), so it is unaffected by the landing rework. `VITE_GOOGLE_MAPS_API_KEY` now only upgrades the signup autocomplete, not the landing.
